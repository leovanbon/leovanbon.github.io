### Emilia where r u

Let's start by locating the parts:

![](attachment/Pasted%20image%2020260816221342.png)

From this, we can conclude that `var_3B80` is the state variable.

The init block prepares the bit string and seeds the machine:

![](attachment/Pasted%20image%2020260816225435.png)

The dispatcher fetches a new state value and passes it to the check chain:

![](attachment/Pasted%20image%2020260816231508.png)

Each dispatcher check block has this format:

```
trigger = cmp_const ^ unk_140001E350[idx]

if state_var != trigger:
	goto next_check_block;
else:
	run_this_case_body();
```

Each matched dispatcher block falls through into a generated case body, and they all have this general behavior:

![](attachment/Pasted%20image%2020260816234707.png)

Each case consumes one nibble from the bit array and transforms the state for the next dispatcher pass.

![](attachment/Pasted%20image%2020260816235044.png)

With that information, we can try emulating to find the nibbles.

The blind worst case is `O(16^k)`, which would be impossible for this challenge: `k = 110`.

However, each state has concrete values for `x := var_3B78` and `y := var_3B88`; most guessed nibbles lead to an `x` that never hits useful dispatcher triggers; the loop has a hard cap of `0x33c = 828` ticks.

With a bit more pruning, we get this core searcher:

```python
def solve():
	cases = extract_dispatcher_cases()
	cases_by_trigger = {case.trigger: case for case in cases}
	
	queue = [{
		"x": 0xee47dd44,
		"y": 0x5c3e3dc7,
		"ticks": 0,
		"nibbles": {},   # nibble_index -> nibble_value
	}]
	
	seen = set()
	
	while queue:
		state = queue.pop(0)
	
		x = state["x"]
		y = state["y"]
		ticks = state["ticks"]
		nibbles = state["nibbles"]
	
		while ticks <= 0x33c:
			ticks += 1
		
			y = (y * x * x * x - 0x90aa - x) & 0xffffffffffffffff
		
			case = cases_by_trigger.get(y)
			
			if case is None:
				continue
			
			if case.is_emilia_loader:
				return nibbles
			
			idx = case.nibble_index
			
			if idx in nibbles:
				candidates = [nibbles[idx]]
			else:
				candidates = range(16)
			
			for nibble in candidates:
				new_nibbles = nibbles.copy()
				new_nibbles[idx] = nibble
				
				new_x = emulate_case_body(case, x, nibble)
				
				next_state = (
					new_x,
					0x5c3e3dc7,
					ticks,
					tuple(sorted(new_nibbles.items())),
				)
				
				if next_state in seen:
					continue
				
				seen.add(next_state)
				
				queue.append({
					"x": new_x,
					"y": 0x5c3e3dc7,
					"ticks": ticks,
					"nibbles": new_nibbles,
				})
		break
```

### Dynamic & asm

I loaded it into IDA, but the obfuscation seems too strong for IDA to handle, so I used another approach.

The imports have these interesting entries. My guess was that it did something with the username and sent it somewhere online.

![](attachment/Pasted%20image%2020260817160927.png)

The PE also creates a file named `flag.txt.emilia`, so I set these breakpoints:

![](attachment/Pasted%20image%2020260817210314.png)

`GetUserNameA` hits first and writes my VM username to the stack. Then the code concatenates it with something, `UNK`.

![](attachment/Pasted%20image%2020260817221013.png)

The next breakpoint to hit was `CreateFileA("flag.txt", GENERIC_READ, FILE_SHARE_READ, NULL, OPEN_EXISTING, FILE_ATTRIBUTE_NORMAL, NULL)`.

It then calls `CreateFileA("flag.txt.emilia", GENERIC_WRITE, 0, NULL, CREATE_ALWAYS, FILE_ATTRIBUTE_NORMAL, NULL)`.

![](attachment/Pasted%20image%2020260817224212.png)

The pattern here is that it encrypts `flag.txt` into `flag.txt.emilia` with something derived from the concatenated string.

I created a test `flag.txt` and ran the binary again.

The next breakpoints to hit were `ReadFile` and `WriteFile`:

![](attachment/Pasted%20image%2020260817231204.png)

Here, note that `rdx`, the second argument, is the destination/source buffer pointer for `ReadFile`/`WriteFile`. The encryption function should lie between them because `rdx` is loaded from the same source, `[rsp+78]`.

By stepping through, I excluded the other candidates and confirmed that this is the encryption function:

![](attachment/Pasted%20image%2020260817234255.png)

At this point, the function looks like `encrypt(buf, len, key)`.

![](attachment/Pasted%20image%2020260817234813.png)

I checked `[r8]` in the dump. It is a 32-byte blob.

![](attachment/Pasted%20image%2020260817235204.png)

The previous analysis suggests that this could be `sha256("UNK_" + username)` or something similar.

Jackpot.

![](attachment/Pasted%20image%2020260817235523.png)

With the encryption key located, I set a hardware breakpoint on that `clb_dep_trai` buffer, which got me to this part:

![](attachment/Pasted%20image%2020260818004531.png)

Given that this is inside `bcryptprimitives.dll`, it is likely RC4 here. A later external test confirmed it.

The hardware breakpoint only hits inside that loop, so we can conclude that it uses RC4 to encrypt `flag.txt` into `flag.txt.emilia`.

The prompt said to "follow its trail beyond the victim machine, and determine what additional evidence can be recovered", so let's keep digging to get the real `flag.txt.emilia`.

## Flag

Based on what we have found, the SHA-256 of the name fields from the `.cab` filename is used as the RC4 key to encrypt the flag. This script should give us the flag:

```python
from hashlib import sha256
from pathlib import Path
from Crypto.Cipher import ARC4

key = sha256(b"NEX0_Nexo").digest()
ct = Path("flag.txt.emilia").read_bytes()

pt = ARC4.new(key).decrypt(ct)
print(pt.decode())
```
